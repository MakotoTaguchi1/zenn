## 1. はじめに

私はプロジェクトで TS・JS 系言語を使った開発をしています。
パッケージの更新や CI 高速化に取り組む中で、Node.js の依存関係やパッケージマネージャを曖昧なまま使っていたことに気づきました。そこで、今回自分の言葉で記事にまとめて理解を深めてみようと思いました。

普段見慣れているファイルやコマンドでも意外と奥が深いので、ぜひ Node.js 開発をしている方に読んでいただきたいです！

この記事で扱う主な内容

- ロックファイルとは？

## 2. そもそもパッケージマネージャとは？

### パッケージとは

パッケージとは、コードやツールなどを、パッケージマネージャで配布・インストールできる単位にまとめたものです。npm におけるパッケージは、`package.json` によって内容や依存関係などが記述されます。

例えば、`axios` や `dayjs` は、ライブラリとして利用できる代表的な npm パッケージです。
これらを自分でゼロから実装する代わりに、プロジェクトに取り込んで利用させてもらうことで開発を楽にできます。

### package.json はパッケージマネージャではない

ここでよくある誤解ですが、**`package.json` 自体は、パッケージマネージャではありません。**

「`package.json` とは何か」「パッケージマネージャとは何か」と違いを聞かれると、簡潔に説明するのは意外と難しく詰まってしまう人も多いのではないでしょうか（私もそうでした）

`package.json` は、**パッケージマネージャが読み込む「設定ファイル」** という立ち位置です。
以下のような情報を記述します。

- 依存パッケージの一覧とバージョン範囲（`dependencies`、`devDependencies`）
- `npm run build` のように実行できるスクリプト定義（`scripts`）
- プロジェクトのメタ情報（名前、バージョン、ライセンスなど）

### パッケージマネージャとは

一方**パッケージマネージャ**は、`package.json` に書かれた情報をもとに、実際にパッケージの**インストール・更新・削除**を行うツールです。代表的なものに `npm`、`Yarn`、`pnpm` があります。

つまり、`package.json` が「何を使いたいか」という**意図の記述**であるのに対し、パッケージマネージャはその意図を読み取り、実際に依存関係を解決・構築する**実行主体**である、という関係になります。

では、その「実行」の中で具体的に何が行われているのでしょうか。次のセクションで見ていきます。

## 3. パッケージマネージャが行う 5 つのこと

パッケージマネージャは、package.json を読み込み、依存関係を解決してから、ロックファイルと node_modules を生成・更新します。

```text
package.json
  許容する依存関係
       ↓ パッケージマネージャが依存解決
package-lock.json
  実際に採用した依存ツリー
       ↓ インストール
node_modules
  実際に配置されたファイル
```

主な役割は次の 5 つです。

**a. 依存解決**

package.json のバージョン範囲を読み、実際にインストールするバージョンを決定します。複数のパッケージが同じパッケージを要求している場合は、1 つにまとめられるか、複数バージョンを配置する必要があるかも判断します。

**b. レジストリとの通信とダウンロード**

registry.npmjs.org などのレジストリからパッケージの実体（tarball）を取得し、展開・配置します。

**c. ロックファイルの生成・更新**

解決した正確なバージョン、取得元 URL、integrity ハッシュなどをロックファイルへ記録します。

**d. スクリプトの実行**

package.json の `scripts` フィールドに定義されたコマンドや、`postinstall` などのライフサイクルスクリプトを実行します。

**e. 整合性検証**

ダウンロードしたパッケージが、ロックファイルに記録された integrity ハッシュと一致するか検証します。

:::message
`package.json` は **「依存関係の意図」**、ロックファイルは **「依存解決の結果」**、`node_modules` は **「インストールされた実体」** と表現できます。
:::

## 4. 直接依存と推移的依存

プロジェクトが利用する依存パッケージは、直接依存と推移的依存に分けられます。

### 直接依存

- プロジェクト自身が利用するために追加したパッケージ
- `package.json` の `dependencies` や `devDependencies` に記載される

例えば、npm で `axios` をインストールします。

```bash
npm install axios
```

すると、`package.json` の `dependencies` に `axios` が追加されます。バージョンは例です。

```json
{
  "dependencies": {
    "axios": "^1.7.0"
  }
}
```

### 推移的依存

推移的依存とは、直接依存しているパッケージが、内部で必要としている別のパッケージのことです。
自分で追加していなくても、依存関係をたどってインストールされます。

例えば、プロジェクトが `some-api-client` を直接利用し、そのパッケージが内部で `axios` を利用している場合、依存関係は次のようになります。

```text
my-app
└── some-api-client  ← 直接依存
    └── axios        ← 推移的依存
```

このとき、**npm、Yarn、pnpm などのパッケージマネージャが、各パッケージの依存範囲を把握した上で推移的依存パッケージのバージョンを決定**します。
一度解決したら、package-lock.json（yarn.lock や pnpm-lock.yaml）に固定され、次回のインストール以降でバージョン決定のアルゴリズム計算をする手間を省略できます。

:::message
`package.json` に明示するのは **直接依存** です。ロックファイルには、直接依存だけでなく **推移的依存を含む依存ツリー全体の解決結果** が記録されます。
:::

## 5. 【コラム】バージョンを完全に固定しない理由

少し脇道に逸れますが、ここは個人的に気になっていた部分なので調べてみました。

package.json を眺めていると、`^4.18.0` のような `^` の表記をよく見ますよね。
これはバージョンの**範囲指定**です。

```json
{
  "dependencies": {
    "express": "^4.18.0"
  }
}
```

`^4.18.0` は `4.18.0` 以上 `5.0.0` 未満のバージョンを許容する指定です。

バージョンを範囲で指定する理由は、主に次の 2 つがあるようです。

1. 互換性を維持したまま、**バグ・セキュリティ修正を含む更新を取り込みやすくする**
2. 複数のパッケージが要求するバージョン範囲をまとめ、**同じパッケージを共有しやすくする**

例えば、次の依存関係は要求するバージョン範囲が重なっています。

```text
package-a → lodash ^4.17.0
package-b → lodash ^4.18.0
```

両方の範囲を満たすバージョンがあれば、1 つの `lodash` を共有できます。
一方、次のように**範囲が重ならない場合は、異なるバージョンを複数配置しなければなりません**

```text
package-a → lodash ^4.17.0
package-b → lodash ^5.0.0
```

ただし、ロックファイルが存在する場合、インストールのたびに許容範囲内の最新版へ更新されるわけではありません。

```text
package.json:      ^4.18.0  ← 許容するバージョン範囲
                       ↓ 依存解決
package-lock.json: 4.18.2   ← 実際に使うバージョンを固定
                       ↓ インストール
node_modules:      4.18.2
```

:::message
`^` による範囲指定は、更新を自動で取り込む仕組みではありません。**ロックファイルが存在する限り、インストールのたびに許容範囲内の最新版へ更新されるわけではない**点が重要です。

実際の更新は、`npm update` や Dependabot・Renovate などを使って意図的に行います。
:::

## 6. package.json とロックファイルの関係

まず、両者の役割を具体例で確認します。

例として axios に依存している some-api-client というパッケージのみを利用する場合は、以下になります

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "dependencies": {
    "some-api-client": "^2.1.0"
  }
}
```

ポイントは、この**package.json 自体には axios という文字列は一切登場しない**ことです。
axios は some-api-client の推移的依存であり、自分のプロジェクトが直接指定しているわけではないからです。

依存関係を簡単に表すと、次のようになります。

```text
my-app
└── some-api-client ^2.1.0
    └── axios ^1.6.0 → 1.6.2に解決
```

実際の `package-lock.json` では、解決されたバージョンや取得元などが記録されます。

:::details package-lock.json の例を見る

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "lockfileVersion": 3,
  "packages": {
    "": {
      "name": "my-app",
      "version": "1.0.0",
      "dependencies": {
        "some-api-client": "^2.1.0"
      }
    },
    "node_modules/some-api-client": {
      "version": "2.1.0",
      "resolved": "https://registry.npmjs.org/some-api-client/-/some-api-client-2.1.0.tgz",
      "integrity": "sha512-aaaa...",
      "dependencies": {
        "axios": "^1.6.0"
      }
    },
    "node_modules/axios": {
      "version": "1.6.2",
      "resolved": "https://registry.npmjs.org/axios/-/axios-1.6.2.tgz",
      "integrity": "sha512-cccc..."
    }
  }
}
```

:::

axios は some-api-client が要求する ^1.6.0 を満たす 1.6.2 が、node_modules のトップレベルに 1 つ配置されます。

これだとシンプルです。
次に、another-http-lib という、これまた axios に依存しているパッケージも利用したい場合はどうなるでしょう。

この場合、それぞれ以下のようになります

package.json

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "dependencies": {
    "some-api-client": "^2.1.0",
    "another-http-lib": "^1.5.3"
  }
}
```

依存関係を簡単に表すと、2 つのパッケージがそれぞれ異なる範囲で `axios` を要求しています。

```text
my-app
├── some-api-client ^2.1.0
│   └── axios ^1.6.0 ─┐
└── another-http-lib ^1.5.3
    └── axios ^1.4.0 ─┴→ 1.6.2を共有
```

:::details package-lock.json の例を見る

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "lockfileVersion": 3,
  "packages": {
    "": {
      "name": "my-app",
      "version": "1.0.0",
      "dependencies": {
        "some-api-client": "^2.1.0",
        "another-http-lib": "^1.5.3"
      }
    },
    "node_modules/some-api-client": {
      "version": "2.1.0",
      "resolved": "https://registry.npmjs.org/some-api-client/-/some-api-client-2.1.0.tgz",
      "integrity": "sha512-aaaa...",
      "dependencies": {
        "axios": "^1.6.0"
      }
    },
    "node_modules/another-http-lib": {
      "version": "1.5.3",
      "resolved": "https://registry.npmjs.org/another-http-lib/-/another-http-lib-1.5.3.tgz",
      "integrity": "sha512-bbbb...",
      "dependencies": {
        "axios": "^1.4.0"
      }
    },
    "node_modules/axios": {
      "version": "1.6.2",
      "resolved": "https://registry.npmjs.org/axios/-/axios-1.6.2.tgz",
      "integrity": "sha512-cccc..."
    }
  }
}
```

:::

another-http-lib を追加すると、package.json は dependencies にエントリが 1 行増えるだけです。
一方、package-lock.json の変更はもう少し大きく、次のエントリが追加されます。

- `packages[""].dependencies` に another-http-lib が追加される
- `node_modules / another-http-lib` のエントリが丸ごと追加される
- `axios` のエントリは両方のパターンで同じ 1.6.2 のまま（another-http-lib の要求^1.4.0 も 1.6.2 を満たすため、既存の axios を共有できてネストは発生しない）

## 7. ロックファイルをどう運用するか

ロックファイルは、直接依存と推移的依存を含む依存ツリーの解決結果を記録し、チームや CI で同じ依存関係を再現するために使います。

パッケージマネージャごとに、生成されるロックファイルは異なります。

- npm: `package-lock.json`
- Yarn: `yarn.lock`
- pnpm: `pnpm-lock.yaml`

### ロックファイルは 1 種類に統一する

:::message alert
同じプロジェクトで `package-lock.json`、`yarn.lock`、`pnpm-lock.yaml` を混在させると、利用するパッケージマネージャによって異なる依存ツリーがインストールされる可能性があります。**チームで使用するパッケージマネージャとロックファイルは 1 種類に統一します。**
:::

チームで使用するパッケージマネージャを決め、対応するロックファイルだけを Git へコミットします。必要に応じて、`package.json` の `packageManager` フィールドで使用するツールとバージョンも明示します。

アプリケーション開発では、ロックファイルを Git へコミットするのが基本です。メンバーごとのローカル環境や CI で同じ依存ツリーを再現でき、依存パッケージの変更もコードレビューで確認できます。

また、ロックファイルは手動編集せず、利用しているパッケージマネージャのコマンドで更新します。CI ではロックファイルを変更しないインストールコマンドを使い、`package.json` との不整合をエラーとして検出します。

### `npm ci` とは

`npm ci` は、既存の `node_modules` を削除したうえで、ロックファイルに記録された依存ツリーをインストールするコマンドです。

:::message alert
`package.json` とロックファイルの内容が一致しない場合、`npm ci` はロックファイルを更新せずに **エラーで終了します**。この厳格な動作により、依存関係の更新漏れを CI で検知できます。
:::

開発者ごとの環境差を減らし、CI で同じ依存ツリーを再現する用途に向いています。

挙動の違いを表にすると、こうなります。

| 項目                      | `npm install`                    | `npm ci`                           |
| ------------------------- | -------------------------------- | ---------------------------------- |
| `package.json` のみの状態 | 動作する（新規に解決）           | エラーになる（ロックファイル必須） |
| ロックファイルとの整合性  | **矛盾があれば調整して進める**   | **矛盾があれば即座にエラー**       |
| `package.json` の更新     | 依存追加時などに書き換える       | 一切書き換えない                   |
| 既存の `node_modules`     | 差分だけ更新                     | 常に削除してから全部入れ直す       |
| 速度                      | 差分計算が入る分、状況により遅い | 差分計算を省略するため**高速**     |
| バージョン決定の再計算    | 必要に応じて行う                 | 新しいバージョンを選び直さない     |

`npm install` が必要に応じて依存パッケージのバージョンを選び直し、ロックファイルを更新するのに対し、`npm ci` はロックファイルに記録されたバージョンを使用します。インストール時に新しいバージョンを選び直さず、`package.json` やロックファイルも変更しません。

`npm ci` は Github Actions などの CI に向いているコマンドです。
理由:

- 再現性: CI 上の毎回違う実行環境でも、寸分違わず同じバージョンの依存関係がインストールされることを保証できる
- 速度: `npm install` より高速なため、完了待ちを軽減できる
- 安全性:package.json とロックファイルがズレている（誰かが手動編集してロックファイルの更新を忘れた等）状態を、インストール前に検知できる

Yarn、pnpm でも `npm ci` と同じく「ロックファイル通りに固定インストール」するコマンドがあります。

- Yarn Classic（v1）: `yarn install --frozen-lockfile`
- Yarn Berry（v2+）: `yarn install --immutable`
- pnpm: `pnpm install --frozen-lockfile`

## 8. まとめ

普段何気なく使っている `npm install` の裏側を、パッケージマネージャ・依存関係・ロックファイルの仕組みに触れながら整理してみました。個人的にも記事を書く中で理解が深まり、とても良い経験でした。

重要なポイントと、実際の運用で意識したいプラクティスは次のとおりです。

- `package.json` は、プロジェクトが直接利用する依存パッケージと、許容するバージョン範囲を記述する「設定ファイル」
- パッケージマネージャは、直接依存・推移的依存を解決し、ダウンロード・整合性検証も行う「実行主体」
- ロックファイルは、推移的依存を含む実際の依存ツリーが記録される。手動編集しない。パッケージマネージャのコマンドで更新する
- 開発現場では、ロックファイルを Git へコミットし、チーム内と CI で同じ依存を再現できるようにする
- CI 上では `npm ci` などの CI 向けのコマンドを使うと良い
- package.json では許容バージョン範囲が書かれていても、ロックファイルが有効ならインストールのたびに最新版へ更新されるわけではない。更新は `npm update` や Dependabot・Renovate などで意図的に行う

`package.json`、ロックファイル、`node_modules` は、それぞれ「意図」「解決結果」「実体」という異なる役割を持っています。
この違いが分かると、依存更新や CI のトラブルでも、どこ確認すべきか切り分けやすくなりそうです！
